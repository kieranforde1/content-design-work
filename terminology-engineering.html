Tool architecture

Three layers of capability.

The in-house checker is designed around three layers of capability. Each layer has to work before the next one is useful — which also gave us a natural sequencing for engineering scoping conversations.

L1
Content Skills
The rules engine — the documented terminology and style guidelines that the checker validates against. This is the knowledge base. Without accurate, complete rules, nothing else works. A significant part of the pre-engineering work has been auditing ~2,500 terms to assess what can be automatically checked and what needs human judgment.
L2
Content Services
The checking mechanism — the logic that reads product text from code reviews and runs it against the rules. This is where the rules-based approach matters: the checker gives a clear, auditable yes/no rather than an AI-generated suggestion that might be inconsistent between runs.
L3
Fix and Reporting Mechanisms
How findings get acted on — surfacing issues to engineers in the code review workflow, routing reports to the content designers responsible for each area, and tracking remediation over time. This layer determines whether the checker changes behaviour or just produces reports nobody reads.

The current version of the Terminology Checker — 270,752 issues identified and grouped by hub and platform layer across 47 product areas. Each area shows Fix, Caution, Review, and Document issue counts.

Key decisions

What I chose and why.

The most consequential decisions in the engineering rebuild weren't about UI. They were about architecture, ownership, and what "good enough" meant at each stage.

✕
Use an AI-powered checker built by our writing platform vendor Not chosen
Writer (our AI writing standards platform) proposed building a fully AI-powered checker that would handle code review end-to-end. The appeal was speed to market — Writer's team would own the build. The risk was loss of control: an AI-powered approach produces inconsistent results, is harder to audit, and creates a dependency on a third-party platform for a core quality function. We also had an unresolved question about whether Writer's knowledge base was accessible via external API or only to Writer's own tools. I recommended against this approach.
✓
Build a rules-based in-house checker, with an optional connection to the writing platform Chosen
A rules-based checker gives consistent, auditable results. Engineers can trust the output and understand why a flag was raised. It keeps ownership of the rules and the workflow inside HubSpot. The architecture allows an optional connection to the writing platform's knowledge base if the API question gets resolved — so we're not closing that door, we're just not depending on it.
✕
Continue as a standalone app Not chosen
The first version of the checker was a standalone web app. It worked well as a proof of concept and for the Code Orange reporting sprint. But a standalone app requires content designers to manually run audits — it doesn't close the loop in the engineering workflow. The highest-leverage intervention is catching issues before they reach users, not after.
✓
Integrate into the code review workflow directly Chosen
Integrating into the code review workflow means the checker runs automatically on every relevant change, without requiring any action from content design. This is the difference between a useful tool and a behaviour-changing one. Engineers get immediate feedback. Content designers get visibility. Issues get caught before production.

Outcomes so far

Work and results so far.

The checker is still in build, but the groundwork has already had measurable impact.

22 targeted reports sent to product owners across Automation, Data Hub, and Reporting — identifying 5,311 issues in total. 501 of those were resolved by teams acting on the reports alone, with no automated tooling. That's a 13.2% fix rate from a purely manual process — evidence that teams act on terminology issues when they're surfaced clearly. The remaining 4,608 are what the engineering checker is built to handle.

Terms assessment complete. A manual audit of the terms workbook identified 67 additional automatable terms — expanding the checker's coverage and unblocking the final engineering scoping.

Engineering partners confirmed. Three engineering partners are committed to the build. Architecture and sequencing are agreed.

Projected coverage improvement. The engineering rebuild is expected to raise automated checking coverage from ~47% to ~77% — a 30 percentage point improvement in the proportion of terminology issues that can be caught automatically.

What's next

Completing the terms assessment and shipping the checker.

The checker running in production is the milestone that takes this from "demonstrated capability" to "shipped infrastructure." The terms assessment is complete; the current focus is working through the build with the engineering team.

Alongside that, there's ongoing work to make the case visible to the new team lead — both because the team reorganisation means they're new to this work, and because their background in centralised content design and string management makes them a natural audience for the argument this project makes.
