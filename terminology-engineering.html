Tool architecture

Three layers of capability.

The in-house checker is designed around three layers of capability. Each layer has to work before the next one is useful — which also gave us a natural sequencing for engineering scoping conversations.

L1
Content Skills
The rules engine — the documented terminology and style guidelines that the checker validates against. This is the knowledge base. Without accurate, complete rules, nothing else works. A significant part of the pre-engineering work has been auditing ~2,500 terms to assess what can be automatically checked and what needs human judgment.
L2
Content Services
The checking mechanism — the logic that reads UI strings from PRs and runs them against the rules. This is where the deterministic approach matters: the checker gives a clear, auditable yes/no rather than an AI-generated suggestion that might be inconsistent between runs.
L3
Fix and Reporting Mechanisms
How findings get acted on — surfacing issues to engineers in the PR workflow, routing reports to content design DRIs, and tracking remediation over time. This layer determines whether the checker changes behaviour or just produces reports nobody reads.

The current version of the Terminology Checker — 270,752 issues identified and grouped by hub and platform layer across 47 product areas. Each area shows Fix, Caution, Review, and Document issue counts.

Key decisions

What I chose and why.

The most consequential decisions in the engineering rebuild weren't about UI. They were about architecture, ownership, and what "good enough" meant at each stage.

✕
Use Writer's fully agentic PR-checking approach Not chosen
Writer (our AI writing platform) proposed building a fully agentic checker that would handle PR review end-to-end. The appeal was speed to market — Writer's team would own the build. The risk was loss of control: an agentic approach is non-deterministic, harder to audit, and creates a dependency on a third-party platform for a core quality function. We also had an unresolved question about whether Writer's Knowledge Graph was accessible via external API or only to Writer's own agents. I recommended against this approach and sent a diplomatic decline to the Writer engineering contact. Jonathon took over the ongoing Writer relationship.
✓
Build a deterministic in-house checker, with optional Writer KG calls Chosen
A deterministic checker gives consistent, auditable results. Engineers can trust the output and understand why a flag was raised. It keeps ownership of the rules and the workflow inside HubSpot. The architecture allows us to optionally call Writer's Knowledge Graph as a knowledge source if the API question gets resolved — so we're not closing that door, we're just not depending on it.
✕
Continue as a standalone app (Lovable/Supabase) Not chosen
The first version of the checker was a standalone web app built on Lovable and Supabase. It worked well as a proof of concept and for the Code Orange reporting sprint. But a standalone app requires content designers to manually run audits — it doesn't close the loop in the engineering workflow. The highest-leverage intervention is catching issues before they ship, not after.
✓
Integrate into the PR workflow directly Chosen
Integrating into the PR workflow means the checker runs automatically on every relevant PR, without requiring any action from content design. This is the difference between a useful tool and a behaviour-changing one. Engineers get immediate feedback. Content designers get visibility. Issues get caught before production.

Outcomes so far

Work and results so far.

The PR checker is still in build, but the groundwork has already had measurable impact.

22 targeted reports sent to DRIs across Automation, Data Hub, and Reporting — identifying 1,673 incorrectly used terms and 3,638 instances potentially needing documentation. Teams are actively working on these changes.

Engineering partners scoped in. Hemerson, Dakota, and Mary are committed to the build. The architecture and sequencing are agreed; the current blocker is completing the terms workbook auto-fix assessment to enable final scoping.

Projected coverage uplift. The engineering rebuild is expected to raise automation coverage from ~47% to ~77% — a 30 percentage point improvement in the proportion of terminology issues that can be caught automatically.
